# evnx v0.5.0 — the command-review release

**Released 2026-09-24.** 31 pull requests (#29–#59) since v0.4.0.

`CHANGELOG.md` carries the summary. This file is the detail: what was wrong,
how it was found, and what was done about it.

---

## Why this release exists

v0.4.0 shipped cloud sync. This one did not add a headline feature — it went
through the commands one at a time, ran each against a real build, and compared
what it did with what `evnx.dev` said it did.

The audit is in [`command_review/`](https://github.com/urwithajit9/evnx) of the
planning repo: every command exercised against a `--all-features` build, and
every `evnx …` invocation in all 66 documentation files resolved against the
real 50-path CLI surface. The headline number was **111 broken invocations
across 29 of 66 files**.

What that turned up was worse than stale docs. Four commands reported success
while doing nothing, or the wrong thing. Those are first below, because they are
the reason to upgrade rather than wait.

---

## Fail-open fixes

A tool that fails **closed** is annoying. A tool that fails **open** is
dangerous, because the clean report is believed. All four of these failed open.

### `evnx migrate --to github` never encrypted anything (#52)

The function named `encrypt_for_github` base64-encoded the plaintext and posted
it to GitHub's API in the `encrypted_value` field. The `crypto_box` dependency
was in `Cargo.toml` and nothing called it.

GitHub's Actions secrets API requires a libsodium **sealed box** —
`ephemeral_pk ‖ XSalsa20-Poly1305(plaintext)`, with the nonce *derived* as
`blake2b(ephemeral_pk ‖ recipient_pk)` rather than random. That is what it now
sends, via `crypto_box`'s `seal` feature.

Proved empirically before and after, not inferred from the code. Five tests fail
if the change is reverted.

**If you ran `evnx migrate --to github` on any earlier version, rotate those
secrets.** They were transmitted in a form anyone who could read the request
could decode.

### `evnx sync` wrote real secrets into `.env.example` (#53)

On the path that *creates* a template, `sync` copied values from `.env` verbatim
— then printed advice to commit the result. `evnx scan` does not read
`.env.example`, so nothing downstream caught it.

Placeholders are now the default.

### `evnx scan` never read `.env.production` (#33)

`is_scannable` kept the `.env*` name check inside `if path.extension().is_none()`.
Rust reports "no extension" only for a dotfile with no further dots, so
`.env.production` yields `Some("production")` and the name branch was unreachable
for **every** dotted variant — `.local`, `.test`, `.staging`, `.development`.

A directory holding `.env` and `.env.production` scanned only the first and
printed a completed-scan summary. The file most likely to hold production
credentials was the one file skipped.

### `evnx scan ./typo` reported "✓ No secrets detected" (#42)

A path that could not be walked produced an empty file list, which rendered as a
clean scan and exit `0`. A CI gate pointed at a renamed directory passed
silently, forever.

`scan` now has a three-value exit contract: `0` clean, `1` secrets found, `2`
the scan could not be completed. **`2` is not a louder `1`** — "I found nothing"
and "I could not look" are different answers. `--exit-zero` suppresses `1` only.

## New: the variable contract — `evnx spec` (#54, #56, #57)

`.env.example` can say a variable exists. It cannot say the variable is required
only in production, must parse as a URL, or holds a credential despite a name
that gives nothing away.

`[vars]` in `.evnx.toml` says those things, and `evnx spec init` writes it by
inferring from the files you already have.

```toml
[vars]
PORT = { format = "port", description = "HTTP listen port" }

[vars.TENANT_A]
secret = true                    # scan reports it; no heuristic could
environments = ["production"]
```

Read by `validate`, `scan` and `sync`. The asymmetry that matters: `secret = true`
adds a finding `scan` could not otherwise reach, and `secret = false` retracts a
guess made from a variable's **name** — but never a match on its **value**. A
variable holding `sk_live_…` is reported however it is declared, because
`.evnx.toml` is committed and one wrong line would otherwise silence a live key
for everyone who clones the repository.

`evnx sync` keeps the contract current rather than letting it drift.

## New: `evnx cloud run` (#55)

```bash
evnx cloud run --vault my-app/production -- ./deploy.sh
```

Decrypts a vault in memory and hands it to a child process. Nothing on disk,
nothing in shell history, and **nothing in `ps`** — values travel in the
environment block, never the argument vector.

- `--include` / `--exclude` narrow what the child sees. Least privilege: a build
  step needing only `NEXT_PUBLIC_*` has no reason to hold your database password.
- A filter matching nothing is an **error**, not a silent run with zero secrets.
- The child's exit code comes back unchanged, so a pipeline can branch on it.
- Runs the command directly, not through a shell. Pipelines need `-- sh -c '…'`.

⚠️ This removes the plaintext *file*, not the master password. The vault key is
wrapped under your master key, so decryption needs it wherever the command runs.
In CI, feed it with `--password-stdin`.

Verified end to end before release, including the `/proc/self/cmdline` check:
[Verifying the Round Trip](https://www.evnx.dev/guides/reference/verifying-the-round-trip).

## New: team sharing (#30, #31)

- **`evnx vault share`** — wraps the vault key for another account using a
  **hybrid X25519 + ML-KEM-768** scheme. There is no X25519-only path; sharing
  with an account that has no ML-KEM key on file is refused rather than
  downgraded.
- **`evnx vault members`**, **`role`**, **`revoke`** — and revocation actually
  revokes: removing a member re-keys the vault, so a member who kept their
  unwrapped copy cannot open versions pushed after removal.

⚠️ The recipient's public keys come from the server. There is no third party to
check them against and out-of-band fingerprint verification is not built, so
"the server cannot read your secrets" becomes "…cannot read them *passively*"
the moment you share.

## New: custom scan patterns (#59)

`--pattern 'ACME-[A-Z0-9]{32}'` for an ad-hoc rule; `[[scan.patterns]]` in
`.evnx.toml` for the named, team-shared kind. Both apply together.

Matching is one `RegexSet` pass over each line — the approach GitHub's scanner
and gitleaks use — so declaring rules stays close to free. Measured over 60,000
lines: 200 patterns cost 68 ms against a 55 ms no-pattern baseline, where
looping over the same rules costs 369 ms.

An expression that does not compile exits `2`. `--exit-zero` does not suppress
it: a broken rule reading as "no secrets found" would be CI passing a search
that never ran.

## `.evnx.toml` now does something (#39)

`core/config.rs` was 383 lines of finished, tested machinery that nothing ever
called, against a schema documented nowhere. It is rewritten around one rule:

> A setting belongs in `.evnx.toml` if it is true of the **project** and would
> otherwise be repeated on every invocation. It does not if it expresses what
> *this* invocation should do.

So `[scan] severity` is configurable and `--exit-zero` is not.

Precedence is flag > config > default. Lists **combine** rather than replace —
`--exclude` adds to the project's standing exclusions instead of discarding
them. Booleans can be tightened by a flag but never loosened.

Settings that can *weaken* scanning are announced on every run:

```
  config    .evnx.toml (scan.severity=high, vars.secret=false on 1 variable(s))
```

Unknown keys warn and never fail, so a file written for a later evnx keeps
working on an earlier one.

## Multiple environments (#37, #38)

`--env-name production` resolves to `.env.production` across `validate`, `scan`,
`diff`, `sync`, `convert`, `backup` and `template`. A name whose file does not
exist is an error listing the ones that do — it never falls back to `.env`.

`evnx diff --env-name production --against staging` compares two real
environments, which is the useful diff; the default compares against a template
where every filled-in value differs by construction.

`init` and `doctor` now cover every env file rather than just `.env`. Verified
with `git check-ignore`: `.env.production` and `.env.staging` were **not**
ignored by the `.gitignore` that `evnx init` wrote.

Cloud commands derive the file from the vault's environment — pushing
`app/production` picks up `.env.production` — and always print which file they
chose.

## CI surfaces

- **`evnx sync --check`** (#34, #35) — the gate that fails. `0` in sync, `1`
  drifted, `2` could not check. Plus `--format json` with a diff summary (#49).
- **`evnx doctor --fix`, `--path`, `--strict`** (#40, #43) — the auto-fix had
  worked since doctor shipped, reachable only through `EVNX_AUTO_FIX=1`. No flag
  exposed it, which is why the guides kept inventing one: `--fix`,
  `--check-config`, `--fail-on-warning`, `--check-example-only` and
  `--check-updates` all appeared in docs and none of them parsed.
- **`evnx scan --format json`** gained a `summary` object (#36). `validate` and
  `doctor` both had one; `scan` was the only machine-readable command without,
  while evnx.dev documented `jq` recipes against `.summary`.
- **Golden-file tests** pin every machine-readable output (#45). `scan
  --format json|sarif|github`, `validate --format json`, `diff --format json`,
  `convert --to …` and `EVNX_OUTPUT_JSON=1 doctor` are parsed by other programs;
  a change to any of them is now a deliberate act.

## `evnx init` (#47, #48)

- `--detect` reads the project and proposes a stack.
- `--from-source` builds the template from what the code actually reads —
  `process.env.X`, `os.getenv("X")`, `std::env::var("X")`.
- `--with` names components directly, skipping the interactive walk.
- `--list-components` prints what is available.

`init` remains **run-once per project**. Making it re-runnable was considered and
rejected: the failure mode of a re-run that overwrites a filled-in `.env.example`
is worse than the inconvenience of using `evnx add`.

## Smaller fixes

- `evnx migrate` now says what it does (#51). Eight of its nine destinations
  print the platform's own CLI commands and never contact it; only
  `github-actions` transfers. The summary said `✓ N uploaded` for all nine.
  `--dry-run` also runs headless now, instead of aborting without a TTY.
- `evnx add` warns when the `.env` it just wrote to is not covered by
  `.gitignore` (#50).
- `evnx template` is strict about unresolved placeholders (#41). `{{ VAR }}`
  with spaces substituted nothing, `|default:` was exactly backwards, and an
  unresolved placeholder was written through with exit `0`.
- `evnx convert` uses the shared header renderer (#58) — the last hand-rolled
  box, found by a documentation sample that reproduced the output.
- Benchmarks compile again, and CI keeps them that way (#44).
- `install.sh` resolves the latest tag without depending on JSON formatting (#29).
- `Cargo.lock` records evnx-crypto's registry source (#32).

## Upgrading

No command was removed. Two flags changed:

- **`evnx validate --pattern` was removed.** Its entire implementation was a
  discarded argument. Use `--env-name` or `--env`.
- **`evnx scan --pattern` now works.** It was accepted and discarded before.
  Same word, opposite directions.

`.evnx.toml` doing nothing on v0.4.x means no project can have depended on it,
so the loader landing is additive in practice.
