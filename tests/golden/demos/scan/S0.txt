$ evnx scan --help
Detect secrets that look real (AWS keys, tokens, etc.).

`evnx scan rules …` manages rule files and `evnx scan hook …` a git pre-commit hook. A folder literally named `rules` or `hook` is scanned as `evnx scan ./rules`.

Usage: evnx scan [OPTIONS] [PATH]...
       evnx scan <COMMAND>

Commands:
  rules  Your own scan rules: list, create and test them
  hook   A git `pre-commit` hook that runs `evnx scan --staged`
  help   Print this message or the help of the given subcommand(s)

Arguments:
  [PATH]...
          Files or folders to scan. Repeatable; defaults to the current folder.
          
          A folder is walked. A file named here is always read — whatever `--exclude`, `--extensions` or the size limit say — and always reported in full, even one git ignores. `-` reads stdin, in memory (`git diff | evnx scan -`): as a `.env` when it parses as one, otherwise as text. Empty stdin is an error, not a clean result.
          
          [default: .]

Options:
      --exclude <EXCLUDE>
          Skip paths in a folder walk. Repeatable; adds to `[scan] exclude`.
          
          A value with `*`, `?` or `[` is a glob, matched against the path from the folder and against the file name: `'fixtures/**'`, `'*.log'`. Any other value matches a whole path component, or several in a row: `--exclude test` skips `test/` and a file named `test`, not `latest/` or `contest.py`; `vendor/cache` skips that folder wherever it is.
          
          ⚠️ This narrows the scan. `.git`, `node_modules`, `target`, `dist`, `build` and the `.env.example` family are skipped whatever this says, and a file named on the command line is read regardless.
          
          [default: .env.example]

      --max-file-size <SIZE>
          Skip walked files larger than this: `500K`, `5MB`, `2MiB`.
          
          Defaults to 1 MiB, or `[scan] max_file_size` from `.evnx.toml`. A skipped file is counted and, with `-v`, listed. A file named on the command line is read whatever its size.

      --extensions <EXT>
          Read only files with these extensions in folders (comma-separated: `env,yml,json`). By default every file is read, and binary or very large files are skipped with a note.
          
          ⚠️ This narrows the scan, and the run says so. A file named on the command line is read whatever this says. `[scan] extensions` in `.evnx.toml` sets the same thing for a project.

      --pattern <REGEX>
          Also report values matching this regular expression. Repeatable.
          
          For the formats evnx does not ship with — an internal token, a vendor key shape. `--pattern 'ACME-[A-Z0-9]{32}'` reports matches as `Custom pattern 1`, numbered in the order the flags are given.
          
          It takes an expression and nothing else. For a name that means something, and for a rule the whole team scans with, declare it under `[[scan.patterns]]` in `.evnx.toml` instead; both sets apply together.
          
          An expression that does not compile exits 2 — no verdict — rather than reporting a clean scan it never ran.

      --ignore-placeholders
          Skip values evnx recognises as filler.
          
          `changeme`, `your_api_key_here`, `xxx` and similar. Useful on a first run over a template-heavy repository; prefer `--severity high` if the goal is simply less noise.

      --no-ignore-placeholders
          Report filler-looking values even when `[scan] ignore_placeholders` is `true`. The last of the two flags wins

      --severity <LEVEL>
          Lowest severity worth reporting: critical, high, medium or low.
          
          Severity is how bad a finding is if it is real: `critical` for cloud, payment and AI keys and private keys, `high` for account tokens, database passwords and variables named like a secret, `low` for test keys and keys meant to ship in a web page. Filters what is reported, counted and exited on. `--severity high` is the usual blocking CI gate. ⚠️ Until 0.13.0 this filtered on confidence; that is now `--confidence`. Defaults to `low` (report everything), or `[scan] severity` from `.evnx.toml`.

      --rules <FILE>
          A rule file for this run, on top of `.evnx/rules/` and your personal rules. Repeatable. Same format as those: see `evnx scan rules new`

      --baseline <FILE>
          Findings accepted earlier: matching ones are reported as `known` and do not fail the run.
          
          Defaults to `.evnx/baseline.json` when it exists. Write it with `--update-baseline`. It holds a fingerprint, a rule and a file per finding, never a value, so it is safe to commit.

      --update-baseline
          Write this run's findings to the baseline (`--baseline`, or `.evnx/baseline.json`) and exit 0. Run it once to accept what a project already has; new findings fail from then on

      --confidence <LEVEL>
          Lowest confidence worth reporting: high, medium or low.
          
          Confidence is how sure evnx is that a match is a real credential of that kind. Combine with `--severity`: both must pass. Defaults to `low`, or `[scan] confidence` from `.evnx.toml`.

      --format <FORMAT>
          Output format: `pretty`, `json`, `sarif` or `github`.
          
          `sarif` uploads to GitHub's Security tab; `github` emits `::error` annotations inline on a pull request; `json` carries a `summary` object for `jq`. An unrecognised value is an error, not a silent fall back to `pretty`.
          
          [default: pretty]

      --exit-zero
          Always exit 0, even when secrets are found.
          
          ⚠️ Suppresses exit 1 only. A scan that could not run still exits 2 — the flag means "do not fail my build over findings", not "never tell me the scan was impossible".

      --include-ignored
          Report findings in files git ignores and does not track.
          
          In a git repository a folder walk counts what git would commit: a filled-in `.env` that `.gitignore` covers is where secrets belong, so its findings are summarised in one line and do not fail the run. This lists them as findings instead. A file named on the command line, and any folder outside a repository, is always reported in full.

      --staged
          Scan what is staged for the next commit, read from the git index.
          
          A file staged and then edited on disk is scanned as staged, because that is what the commit records. Paths limit it to staged files under them. Nothing staged exits 0. `evnx scan hook install` runs this before every commit.

  -v, --verbose
          Enable verbose output

  -q, --quiet
          Print nothing on success. Findings, warnings, errors and requested data still print

      --no-color
          Disable colored output

  -h, --help
          Print help (see a summary with '-h')

  -V, --version
          Print version

What a folder walk reads:
  every file, except .git, node_modules, target, dist and build, the
  .env.example family, editor swap files, binary files (except PKCS#12
  keystores, found by their content), and files over
  1 MiB (--max-file-size). A file named on the command line is always read.
  In a git repository, findings in files git ignores and does not track
  are summarised, not counted (--include-ignored counts them).
